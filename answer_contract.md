# Answer Contract

Defines the structure every AI-generated answer **must** satisfy before it is considered
complete — the output contract of pipeline stage **[11] Answer** in `ai_analytics_architecture.md`
§3. **Specification only** — this is a structural/field contract, not an API schema or code
implementation (no JSON/type definitions are prescribed; a later implementation phase chooses
the concrete serialization).

An answer missing any required field below is **incomplete**, not merely under-detailed — the
architecture must not emit it.

---

## 1. Required fields

| Field | Populated from | Required for |
|---|---|---|
| **Answer text** | Business Reasoning Engine output | Every answer |
| **Trust posture** | `semantic_metric_registry.csv.trust_level` for every metric touched | Every answer |
| **Metric provenance** | `metric_id`(s) actually used | Every answer that cites a number |
| **Calculation provenance** | The exact filters/aggregation/date-field/grain actually applied (from `analytics_execution_spec.md`'s Result object) | Every answer that cites a number |
| **Evidence citations** | Source table/view/diagnostic references (`source_objects`/`validation_reference` columns) | Every answer that cites a number |
| **Validation status** | `MATCH` / `DIFFERS` (with mechanism) / `NOT_DETERMINABLE` (no reference exists) | Every answer that cites a number |
| **Conflict/DQ disclosure** | `conflict_ids`/`dq_ids` for the metric(s), and — for SHOW_BOTH/BLOCK — every competing definition's own value | Any non-SAFE metric |
| **Epistemic labels** | FACT/CALCULATION/OBSERVATION/INFERENCE/HYPOTHESIS/RECOMMENDATION tags per `business_reasoning_spec.md` | Any answer beyond a simple lookup |
| **Confidence** | Per §3 below | Every answer |
| **As-of date** | The business date basis actually used, and — for snapshot-dependent metrics — the reconstruction/query date | Every answer that cites a number |
| **Follow-up affordance** | What clarification or drill-down the system can offer next | Every answer (may be empty for a terminal meta-answer) |

## 2. Evidence citation model

Every cited number must carry a citation chain traceable through all four layers of evidence
already established in this project:

```
Answer number
   -> metric_id (semantic_metric_registry.csv)
      -> source_objects (tables/views actually queried)
         -> file_manifest.csv key (which exported CSV, e.g. F.001, T.journal_entries)
            -> validation_reference (the specific check that confirmed this metric's
               reconstruction logic, e.g. "REV.01, exact match, validation_summary.csv")
```

**A citation is not a footnote appended after the fact — it is generated by the same Execution
step that produced the number**, since the Execution Engine (`analytics_execution_spec.md`) only
ever reads from named, manifest-resolved evidence sources; there is no code path that could
produce a number without this chain already attached.

**Citation format guidance (not a rigid template):** a citation should let a technically-literate
reviewer find the exact evidence file and re-run the check — e.g. "Rs.72,705,593.43, ledger
revenue, `M.REV.001`, validated exact against `F.001` (`v_pnl`), `REV.01` in
`validation_summary.csv`." Verbosity should scale with the user's evident need: a simple lookup
answer might state the citation briefly and offer to expand it; a "why did this number differ"
follow-up should surface the full chain.

## 3. Confidence model

Confidence is **not a single blended score** — per `ai_trust_policy.md` §2, it varies by trust
level and must never be flattened into one number that hides a SHOW_BOTH/BLOCK situation.

| Trust level | Confidence label | Meaning |
|---|---|---|
| SAFE, `validation_status = MATCH` | `HIGH` | Reconstructed and independently confirmed against an exported reference. |
| SAFE, no independent re-validation (e.g. `M.CASH.001`, `M.LIFE.001`) | `HIGH (by construction, not independently re-validated)` | Logic is fully specified from source and structurally sound, but no live re-check occurred in this project's validation pass. |
| DISCLOSE | `MEDIUM`, with the specific DQ/conflict ID(s) named | Usable, but a known limitation attaches. |
| SHOW_BOTH | `SPLIT` — each definition reports its own confidence separately | Never one number for the family. |
| BLOCK | `BLOCKED` | No numeric confidence is ever emitted alongside a refused answer — assigning a score would itself imply a settled number exists. |
| NOT_DETERMINABLE | `UNVERIFIED` | The calculation is possible but has no reference to confirm it. |

**Confidence for HYPOTHESIS/RECOMMENDATION stages** (per `business_reasoning_spec.md`) uses the
same vocabulary already established in `data_quality_report.md`'s `root_cause_confidence`
column — `PROVEN` (independently re-derived and exact-matched) or `SUSPECTED` (evidence-consistent,
not confirmed by an exported query/function definition) — never a numeric percentage, since no
statistical calibration of these labels exists in the evidence.

## 4. Metric and calculation provenance — worked structure

For a single-metric SAFE answer (e.g. "what's our revenue"):

```
Answer: "Ledger-derived revenue (all-time) is Rs.72,705,593.43."
Trust posture: SAFE
Metric provenance: M.REV.001
Calculation provenance: SUM(signed_amount) WHERE account_type='INCOME',
  reversal-excluded, journal_lines x journal_entries x coa_accounts
Evidence citations: F.001 (v_pnl), T.journal_lines, T.journal_entries, T.coa_accounts
Validation status: MATCH (REV.01, validation_summary.csv)
Epistemic label: CALCULATION
Confidence: HIGH
As-of date: entry_date basis, ledger span 2019-11-03 to 2026-09-20
Follow-up affordance: offer monthly breakdown (M.REV.002), or by-account breakdown
```

For a BLOCK answer (e.g. "how much does this tenant owe"):

```
Answer: [refusal-with-explanation shape per ai_trust_policy.md §2 BLOCK]
Trust posture: BLOCK
Metric provenance: M.AR.001A, M.AR.001B, M.AR.001C, M.AR.001D (the whole family)
Calculation provenance: 4 independently-applied definitions, each with its own
  filters/aggregation (see semantic_layer.md §4)
Evidence citations: F.006, F.007, T.tenant_allotments, T.tenant_transactions
Validation status: A/B MATCH each other exactly (AR.03); C/D each independently
  computed, no cross-reference to validate "correctness," only internal consistency
Conflict/DQ disclosure: C.001, C.003, C.005, DQ.002, DQ.019 -- named explicitly,
  with the numeric spread (up to ~120x) stated
Epistemic label: CALCULATION (all four), INFERENCE (the fact that they conflict)
Confidence: BLOCKED
As-of date: ledger span for A/B; "as stored" (no time series) for C; frozen 2026-04
  migration snapshot for D
Follow-up affordance: offer to show the ledger figure (A/B) as the closest safe
  reference point, with the disclosed caveat that it may not match what the tenant
  or the business currently believes is owed
```

## 5. Answer-shape rules by trust level

These restate `ai_trust_policy.md` §2's behavior rules **as structural contract requirements**,
so a later implementation can validate an answer object against a checklist rather than
re-deriving the policy from prose each time:

- **SAFE:** `value` field populated with exactly one number/series; `conflict_ids`/`dq_ids` may
  be empty; `epistemic_label ≥ CALCULATION`.
- **DISCLOSE:** `value` populated; `caveat_text` field **required and non-empty**, sourced
  verbatim from `semantic_metric_registry.csv.caveat_text`.
- **SHOW_BOTH:** `value` field is **structurally a list/set of labelled values**, never a single
  scalar — an implementation that only has room for one number in this field has violated the
  contract, not merely under-served the user.
- **BLOCK:** `value` field is **absent or explicitly null for the "headline" figure** — the
  answer contains explanation and (optionally) the component definitions' individual values
  **each separately labelled**, but no single figure is presented as "the answer."
- **NOT_DETERMINABLE:** `value` field absent; `explanation` field states specifically what
  evidence is missing or unresolved (not a generic "no data").

---

## 6. Consistency and versioning

- **The contract's field set does not change based on question phrasing** — a terse question
  ("revenue?") and a verbose one ("what was our total ledger-derived revenue across the full
  history of the business?") produce answers with the identical set of populated fields; only
  the natural-language framing of the `Answer text` field may vary in length/tone.
- **Re-asking an identical resolved query must produce an identical answer object** for `SAFE`
  metrics (the evidence is immutable — `ai_analytics_architecture.md` §9's determinism
  requirement) and an identical **set of labelled values** for `SHOW_BOTH` (though the natural
  language wrapping them may vary).
- **A metric's trust level changing** (via a future update to `semantic_metric_registry.csv`,
  e.g. after an owner decision resolves a conflict) must be reflected in every subsequent answer
  immediately — the contract has no caching concept that could serve a stale trust posture.
